# 微信转发与合并聊天记录（尽力读取，拒绝伪造）

BabyMemo 使用腾讯 iLink Bot 协议。在入站消息中收到完整子消息的情况下，可以展开并阅读合并转发/引用消息的文字、附带的微信原生语音转写，以及可访问的图片和视频引用。**不等于微信已对 Bot 开放所有转发类型。** 某些客户端可能根本不向 Bot 下发合并转发消息，或者只下发摘要。

## 支持范围

| 消息内容 | 行为 |
| --- | --- |
| 普通文本、合并消息的嵌套文本、引用消息 | 按原有顺序提取；嵌套消息尽可能保留发送者称呼 |
| 内层图片 / 视频 | 如 iLink 提供合法 CDN 媒体引用和 AES 密钥，复用独立媒体队列解密后保存至家庭相册；遵循原有 4 项/每项 50 MiB 上限 |
| 微信自带语音转写 | 作为带「语音转写」标记的历史材料供模型阅读 |
| 无转写的 MP3 语音 | 仅在 iLink 明确标识 MP3 且允许读取加密原件时，通过配置的 OpenRouter Key 尝试 Whisper 识别；失败会注明无法阅读 |
| 无转写的 SILK、Speex、AMR 等语音 | 目前无可靠转码组件，不声称已识别；建议先在微信转文字 |
| iLink 文件附件（.xml、.txt） | 仅对加密、大小受限且 CDN 来源可信的文本附件尝试读取；可解析其中的 recordinfo 文本 |
| 原始合并转发 XML 中的图片 / 视频指针 | 仅记录存在相应条目，不把外部 URL 当成可信微信媒体引用，不能保证取得原件 |
| 上游完全未下发的转发消息或音视频 | 无法读取；需要微信客户端/iLink 协议提供原始数据 |

## 安全与容错约束

- 被转发的内容属于**历史资料**，不允许作为新增、删除、修改记录的直接操作指令。对转发内容的提问使用只读的 LLM 工具集合，工具执行器还有第二道写保护。
- 媒体继续使用经过白名单验证的微信 CDN 和 AES 下载链路；不将 CDN 参数、密钥和私密 URL 放入模型上下文。
- 解析嵌套层级、最多条数、XML 字节数、文本长度、附件和 MP3 大小均设上限；超过限制标记为不完整而不声称成功。
- 媒体保存通过可重试、去重的 Durable Object 队列，不影响独立微信成员会话。单次含多媒体的转发会先收到已接收通知，入库结果另行通知。
- OpenRouter 语音转写使用 `openai/whisper-1`，会产生额外模型调用和费用；仅在原生转写缺失、格式及访问条件符合时尝试。没有 Key 的实例不执行此路径。

## 验收

`npm run verify`、`npm run test:e2e`、`node scripts/wechat-worker-e2e.mjs`。对实际设备应分别发送「逐条转发」「合并转发」「包含 MP3 转写的语音」「普通微信 SILK 语音」「带图片和视频的聊天记录」并观察 iLink 实际提供的原始字段。仓库测试使用虚构家庭数据及模拟 CDN，不向真实微信、OpenRouter 或生产数据写入。

## TypeScript 迁移

新增 `wechat-forward.ts`、`wechat-attachment.ts`；将 `wechat-message`、`wechat-policy`、`wechat-status` 的实现迁移到严格检查的 TypeScript，保留原 `.mjs` ESM 入口供现有调用方逐步迁移。核心源码模块的 TypeScript 比例由约 48% 提升到至少 52%，通过回归测试设置底线。余下的 `.mjs` 媒体流与 Harness 模块仍需分批迁移，以避免一次改动全部运行链路。
