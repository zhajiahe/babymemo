# BabyMemo 微信 Harness：真实场景审查与演进提案

> 状态：**历史风险审查（固定基线 61c0ecd）**。该文包含早期单工具时代的事实判断，**不是当前 main/PR 的功能清单**；最新已实现/待验收状态请看 [ReAct 架构与实施边界](wechat-harness-implementation.md)、[ReAct R-001～R-014 验收](wechat-harness-test-plan.md)。\n\n> 原始记录：**设计提案 / 待实施**。静态审查基线：main 提交 [61c0ecd](https://github.com/zhajiahe/babymemo/commit/61c0ecd5fc795ee0dde7780493b198d58982ef03)，2026-10-13。未连接真实微信、真实 OpenRouter、生产 D1/R2，也未执行真机验收。对应自动化方案见 [微信 Harness 场景测试计划](./wechat-harness-test-plan.md)。

## 1. 目的和原则

BabyMemo 不是通用 AI 聊天工具。它让家庭成员通过微信私聊记录、查询、更正与整理宝宝的成长数据，所有数据库事实由 D1/R2 提供。产品验收应从家长实际操作出发：口语表达、拆成多条消息、说错再更正、多宝宝、旧照片、重复发送、网络超时，而非只测规范的「调用某工具」格式。

**目标次序：不误写、不串宝宝、不丢记录 > 可恢复 > 交流自然 > 延迟和费用。**

当前系统的安全基础值得保留：绑定账户私聊、白名单工具、D1 精确执行、记录编号/日期歧义拒绝、消息 ID 幂等、媒体下载白名单/格式校验、30 天删除回收站、OpenRouter 重试与写入分离、DO 短期上下文。**以下提案不意味着它们已实现。**

## 2. 当前架构与事实边界

- **消息入口**：src/wechat.ts；iLink Durable Object 轮询、过滤绑定用户和群聊、处理文本或媒体、加密回复及消息 ID 去重。
- **命令解析**：OpenRouter Function Calling，从 src/wechat-harness.mjs 的白名单选择**至多一个**工具；多于一个调用将被拒绝。
- **执行**：runWechatTool 校验动作、日期/编号/数值并通过 D1 查询或写入；LLM 无任意 SQL 权限。
- **短期上下文**：src/wechat-memory.mjs，最多 4 轮、20 分钟 TTL；从上次回复文本提取最多 10 个查询结果的编号，支持有限的「第一条」引用及追问补全。
- **图片/视频**：src/wechat-media.mjs 独立下载解密、私有 R2 入库和 D1 媒体索引；每条最多 4 项、单文件 50 MiB；保存日期默认为微信消息时间对应的宝宝时区本地日期。
- **现有测试**：scripts/wechat-harness.test.mjs、scripts/wechat-memory.test.mjs、scripts/wechat-media.test.mjs、scripts/wechat-video.test.mjs、scripts/openrouter-retry.test.mjs；本地 Worker/Chromium/WebKit 自动 E2E 和手动真实 OpenRouter 工具调用测试。详见 [现有 QA 矩阵](./qa-regression-matrix.md)。

## 3. 按家长真实操作审查

**证据级别**：「已确认」表示从固定提交的控制流可直接看出能力限制或校验空缺；「待验证风险」表示发生频率、具体错误结果仍需带 Mock/真微信场景复现。优先级 P0 为数据准确性或错误写入风险，P1 为高频体验障碍，P2 为性能/扩展项。

| ID | 家长实际说法或动作 | 当前行为 / 问题 | 级别 | 优先级 | 理想结果 |
| --- | --- | --- | --- | --- | --- |
| H-01 | 「今天 10.5kg，昨晚睡不好，顺便记录第一次走路」 | 模型被限定单个工具；多调用直接拒绝，不能完成多项独立记录 | 已确认 | P1 | 拆解成可审核的多步骤任务，分别反馈结果 |
| H-02 | 「记一下体重」→「10.5 公斤」→「昨天」 | 只靠最近聊天文本 + 关键词补全，无结构化待办和缺参状态 | 已确认 | P1 | 明确 pending_task/缺失字段，逐轮补齐 |
| H-03 | 「今天 10.5kg」→「不是，是 10.2」 | 更新需要特定关键词及日期/编号，不能稳健理解省略式纠错 | 已确认 | P1 | 引用上次成功操作、确认后更正并保留版本 |
| H-04 | 发照片 → 「这是昨天拍的，记作第一次走路」 | 上传结果只以回复文字进入记忆；没有可操作的 recent_media_batch；文字和媒体被分支处理 | 已确认 | P1 | 关联照片批次、修改日期、创建里程碑 |
| H-05 | 同一条微信附图写「给小好记个里程碑」 | 有媒体时优先媒体分支，文字最多作为 caption，不会同时执行成长事件工具 | 已确认 | P1 | 图片先入库，再按明示意图补任务；禁止隐式写入 |
| H-06 | 「先记小贝体重」，随后发无附文照片 | 多宝宝收图优先持久化默认宝宝，再使用最近会话宝宝；可能与刚切换的宝宝不同 | 已确认规则 / 待验证风险 | P0 | 显示归属冲突并要求确认，不能静默挂错宝宝 |
| H-07 | 发旧照片并写「这是去年 10 月 1 日拍的」 | 存储日期取微信消息时间；不会用附文日期改写拍摄日期 | 已确认 | P1 | 明确原始拍摄时间和描述时间来源、允许更正 |
| H-08 | 信号差，用户重新发送同一测量文字 | 不同微信消息 ID 允许分别入库；消息级幂等不等于业务级去重 | 已确认 | P0 | 同宝宝/日期/字段值在短窗提示疑似重复，保留真实多次测量能力 |
| H-09 | 「不要删除昨天的记录」 | 删除执行层检查是否含「删除/删掉」，没有确定性的否定语义阻断；若模型误选工具有误删风险 | 待验证风险 | P0 | 明确否定/条件命令永不执行破坏性操作 |
| H-10 | 「今天大概 20 斤」「昨天好像 10.5kg」 | 数值范围校验已存在；缺原文单位、时间指代和不确定性的来源核对 | 已确认校验缺口 / 待验证风险 | P0 | 保留原文证据、确定性单位换算，不确定先追问 |
| H-11 | 「把 10 月 1 日那条改到 10 月 2 日」 | 日期 groundedTarget 仅检查旧日期可在文本找到，不能验证“旧日期/新日期”的语义角色 | 已确认校验边界 | P0 | 分离 selector.day 与 changes.newDay 并核对来源 |
| H-12 | 「撤销刚才那次修改」 | 删除有回收站；更新没有统一 last_operation/修改历史/撤销工具 | 已确认 | P1 | 按操作凭证执行条件撤销；与其它修改冲突时拒绝 |
| H-13 | 「看看我刚删了什么」 | 未指定种类时 list_trash 默认 growth，遗漏相册/成长瞬间 | 已确认 | P1 | 汇总所有类型或明确询问种类 |
| H-14 | 「找上次去医院那条」「查过去 30 天体重」 | 查询主要支持日期和有界最近列表，缺时间区间/关键词/聚合 | 已确认 | P1 | 时间范围、关键词及受限统计，无须上向量库 |
| H-15 | 先查宝宝 A，再说宝宝 B 的「第一条」 | 旧对话回复作为模型上下文；宝宝切换不强制清除上轮结果引用，存在引用混淆风险 | 待验证风险 | P0 | 查询结果绑定 babyId、类型、有效期及确切 ID |
| H-16 | 「昨天」指令在午夜附近或重试后处理 | 相对日期由 Worker 当前时间解析；实际消息发送时间和执行时刻可能跨日 | 待验证风险 | P0 | 按可信消息时间戳和宝宝时区解析相对日期 |
| H-17 | 连发大视频与一条简短查询 | 单一 DO alarm 中串行处理，媒体 CDN/R2 或模型重试可能阻塞后续消息 | 已确认处理方式 / 待验证延迟 | P2 | 有界任务队列、耗时任务分流和有序反馈 |
| H-18 | 「补充过敏：牛奶」 | 更新宝宝资料时 allergies 字段按整体替换，不是自动追加；可能覆盖旧信息 | 已确认执行语义 / 待验证用户理解 | P0 | 区分“追加”与“覆盖”，覆盖原值需回显确认 |
| H-19 | 「现在称体重 10.5」→「取消」 | 没有明确的 pending_action 取消和最近成功操作撤销之区分 | 已确认 | P1 | 区分未执行取消与已执行补偿 |
| H-20 | 「改第一条」但上轮只返回含多个宝宝/类别的结果 | 编号从聊天回复正则抽取，缺受信任的结构化查询结果集 | 已确认实现方式 / 待验证风险 | P0 | 用服务端 last_query_results 绑定归属/类型/ID/顺序 |
| H-21 | OpenRouter 429、模型无 tool_calls、格式不合法 | 已有有限重试和拒绝，但模型选错动作/字段的业务评估样例少 | 已确认覆盖不足 | P1 | 场景语料集、错误码、不可误写断言 |
| H-22 | 微信送达确认中断或批量消息重放 | 已有消息去重、加密回复和 client_id，但「写入→回复」全过程异常窗口需故障注入验证 | 待验证风险 | P0 | 重放绝不二次写；发送失败重试复用结果及 client_id |

## 4. 建议的最小架构

不要加入第二个通用 Agent、向量记忆、GraphRAG、VPS 或 Web AI 助手。保留 Cloudflare Worker + DO + D1/R2 + OpenRouter。

1. **Intent Planner**：模型仅产出受版本控制的结构化意图（可为 0..N 个步骤）。不允许模型直接提交 SQL；遇到歧义则产出 clarification。
2. **Context Resolver**：服务端解析目标宝宝、消息发送时间、明确记录 ID、最近一次查询、最近上传批次；有冲突时不猜测。
3. **Pending Task**：DO 保存 taskId、babyId、待补字段、允许的步骤、expiresAt 和 revision；新话题、取消或超时可终止。
4. **Policy & Validator**：对模型抽取的每个字段检查允许的动作、原文证据、单位、日期角色、否定/条件语句、目标唯一性、风险等级。拒绝的操作不可写库。
5. **Tool Executor**：D1/R2 执行带业务键的受控步骤；写入成功后记录结构化操作凭证，包括 before/after、实体 ID、babyId、时间和执行状态。根据动作实现条件撤销，不允许盲回滚别人的后续变更。
6. **Result Formatter**：只以真实数据库结果汇报已完成、待补充、拒绝和部分成功；重复消息复用之前持久化结果。

### 4.1 建议持有的最少状态

| 状态 | 位置 | 最小字段 | 约束 |
| --- | --- | --- | --- |
| pending_task | Durable Object | taskId、bot/user、babyId、steps、missingFields、expiresAt、revision | 短 TTL；明确取消；重绑、切宝宝时检查冲突 |
| last_query_results | Durable Object | queryId、babyId、kind、orderedIds、expiresAt | 只由 D1 查询生成；不得从模型/聊天文本伪造 |
| recent_media_batch | Durable Object | messageId、babyId、mediaIds、createdAt、expiresAt | 只引用已成功索引的媒体；批量更正前核对 |
| last_operation | D1 操作日志 + DO 最近指针 | operationId、messageId、kind、recordId、before/after hash、revision、status | 防重放、审计及条件撤销；不存明文模型思维过程 |

不要把用户真实病史、照片二进制、微信密钥、OpenRouter 密钥或未经脱敏的完整对话写入调试日志。若增加 D1 表，使用**前向兼容迁移**，不更改既有迁移。

### 4.2 安全策略

- **读取**：允许无副作用查询，有界分页。
- **新增**：必须有用户明确授权的字段与来源证据；疑似重复先反馈。
- **更新**：精确 recordId + babyId + kind + 预期版本；不确定时不写入。
- **删除/批量更新**：明确意图与目标，否定、条件表达、不唯一、跨宝宝、跨类型一律阻断；大批量操作需要确认。
- **撤销**：必须是可验证的最近操作；若已有后续修改冲突则拒绝并提示人工处理。
- **多步骤**：每一步独立持久化状态和幂等键 (taskId, stepIndex)，支持部分成功说明；不能声称数据库回滚了实际上已完成的步骤。

## 5. 阶段实施顺序与验收

| 阶段 | 先交付什么 | 验收门槛 |
| --- | --- | --- |
| S0：测试基线 | 固定场景语料、模拟时钟、可故障注入的 D1/R2/iLink/OpenRouter；保留当前基线预期 | 所有已有测试不退化，危险操作负例有零写入断言 |
| S1：正确性护栏 | 时间/单位/否定/目标来源校验，多宝宝媒体冲突提示，业务级重复检测 | P0 风险场景自动化通过，未授权写入为零 |
| S2：结构化上下文 | pending_task、last_query_results、recent_media_batch、last_operation | 跨轮补全、切宝宝、超时和引用不混淆 |
| S3：多步和补偿 | 多步骤执行、部分成功反馈、版本化更正与条件撤销 | 故障注入无额外写入；审计可复现 |
| S4：查询与吞吐 | 日期区间/关键词/统计，媒体任务隔离与可观测性 | 查询准确、无泄露、响应延迟不显著退化 |

**不建议直接用 Decision Model 替换执行层。** 如需试验，可将其作为可关闭的 Planner 路由候选，使用同一份冻结测试集与原有 LLM 比较：意图/参数准确率、误写数、拒绝率、p95 延迟和费用。做不到准确性提升就不引入。

## 6. 非目标和变更约束

- **当前已发布版本仍按一条指令最多一项工具操作执行。** 放宽此限制属于未来产品/代码变更，必须同步更新 AGENTS.md 的现行安全约束并增加相应测试；不能只改提示词。
- 不新增医疗诊断、处方建议、自动读取图片理解内容或匿名媒体 URL。
- 文档没有授权生产环境改动：不改 D1/R2 数据，不重绑微信，不轮换密钥，不自动运行收费的模型验证。
- 未来每一项能力都需在 [Harness 测试计划](./wechat-harness-test-plan.md) 中取得明确覆盖状态后才能声称已上线。
